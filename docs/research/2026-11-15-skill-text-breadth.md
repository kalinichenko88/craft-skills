# Make the core of a skill narrow, move the cases into checks

Research of 2026-11-15, for the craft plugin. Sources: Anthropic, OpenAI, published measurements and practitioners; the project's own counts are marked as such.

The choice between "a general frame" and "text for each case" is the wrong question. The sources and the project's data give a third answer: **the specific rules stay in the text, and the list of cases leaves the text** and goes into scripts, tests and evals (an eval is a repeatable run of an agent with a check of the result). Anthropic directly advises against a "laundry list of edge cases". In August 2026 OpenAI rewrote its `skill-creator`, and it now says: "Do not turn a particular example, past failure, or personal preference into a universal requirement". A return to general descriptions is also not correct: in the project's evals a general line kept 0 of 5 Haiku runs on the project's layout, and the same rule as a trigger with its concrete results kept 5 of 5 (#190). No one has measured a length threshold after which a skill stops working. Other things are measured: the share of answers that obey all the rules at the same time falls as a product; unnecessary text on the topic decreases accuracy; instruction files increase the cost by approximately 20 % with no increase in success. By the project's count, the most expensive part of the plugin is not the long `SKILL.md` files. It is the side files of `github` and the shared rules file, which goes into each session. The direction: stop the growth of the text with an admission rule, make the text that is always read shorter, and start to count the misses in real sessions, because nothing counts them now.

## Both vendors give the same advice: a rule follows a measured failure, the form follows the risk

This section contains advice, not measurements. The exceptions are marked.

Anthropic names both errors that the authors of the plugin went through. The first: "vague, high-level guidance", which gives the model no specific signals. The second: "hardcoding complex, brittle logic", which is fragile and expensive to maintain. Between them is the "right altitude": specific enough to guide, and flexible enough for the model to apply heuristics ([Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). The same text says: teams frequently put a list of cases into the prompt, "We do not recommend this", and different canonical examples are necessary instead. The goal is the "minimal set of information that fully outlines your expected behavior", and "minimal does not necessarily mean short". The size itself is not the goal. The goal is to have no text that does not change behaviour.

For skills, Anthropic gives a rule to select the level of detail: "Match the level of specificity to the task's fragility and variability". Where there is one safe path, exact steps are necessary, and a script is better. Where there are many paths, a general direction is necessary. The text is written after the eval: "Create evaluations BEFORE writing extensive documentation", then "just enough content to address the gaps and pass evaluations" ([Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)). The numbers in these documents are advice with no published measurements: a `SKILL.md` body of up to 500 lines and up to 5,000 tokens ([Agent Skills overview](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)), a `CLAUDE.md` of up to 200 lines ([Claude Code: Memory](https://code.claude.com/docs/en/memory)).

For a rule that the model skips, the Claude Code documentation gives two solutions, and a new sentence is not one of them: "If it's a rule that can't bend, turn it into a hook or a deny rule. If the line is getting lost in a long file, the file needs to be shorter." Emphasis with capital letters is called out of date: "piling on emphasis mostly makes Claude over-apply the rule" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)). A third solution comes from the Fable 5.2 page: "rewrite absolute rules with their scope and reason" ([Prompting Claude Fable 5.2](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2)). The number of hooks also has a limit: each hook sometimes fires for no reason, and it must be maintained.

The new Anthropic models follow the text more exactly, and this changes the cost of each sentence. The page about Fable 5 says: "Skills developed for prior models are often too prescriptive for Claude Fable 5 and can degrade output quality" and advises you to delete old instructions if the result is better without them ([Prompting Claude Fable 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5)). The page about Fable 5.2 describes the same growth mechanism that the plugin has: the warnings accumulate, and the model obeys each one. It contains one Anthropic measurement: a wide rule about approval for "sending messages to people outside this conversation" made the model hold back **approximately half of the usual requests** to colleagues ([Prompting Claude Fable 5.2](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2)). The conclusion for authors: a sentence written for one case is now obeyed word for word, and for the adjacent cases too. Opus 4.8, on the contrary, does not transfer a rule to an adjacent object without an explicit scope ([Prompting Claude Opus 4.8](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-4-8)). Thus a rule with a scope and a reason replaces some sentences about cases.

OpenAI goes the same way and speaks about skills directly. The GPT-6 guide says that the model "can be more sensitive to instructions contained in skills and other files", and that they "strongly recommend" a check of such files. An unclear or contradictory instruction in a skill "may cause the model to pause and block work early" ([Using GPT-6](https://developers.openai.com/api/docs/guides/latest-model/gpt-6-astra#prompting-best-practices)). The GPT-5 and GPT-5.1 guides show the typical failure: a general rule "Always…" and a later exception that does not name it. The correction is not a new sentence at the end. It is one conditional rule in the place of the old one: "clarify conflicting rules, remove redundant or contradictory lines, tighten vague guidance" ([GPT-5 prompting guide](https://github.com/openai/openai-cookbook/blob/main/examples/gpt-5/gpt-5_prompting_guide.ipynb), [GPT-5.1 prompting guide](https://github.com/openai/openai-cookbook/blob/main/examples/gpt-5/gpt-5-1_prompting_guide.ipynb)). The Codex guide answers the authors' question almost word for word: an edit that comes from one failure can be "overly specific to that particular situation", it is simplified to a general improvement and checked with an eval ([Codex prompting guide](https://github.com/openai/openai-cookbook/blob/main/examples/gpt-5/codex_prompting_guide.ipynb)).

The current `skill-creator` in `openai/codex` contains three sentences against growth by cases: remove "speculative edge cases"; do not turn a past failure into a general requirement; "Prefer a narrow correction to accumulating universal rules for every observed example". The risk sets the level of detail: exact steps, scripts and absolute words go only where correctness, safety, permissions or a fragile process make them necessary ([skill-creator SKILL.md](https://github.com/openai/codex/blob/main/codex-rs/skills/src/assets/samples/skill-creator/SKILL.md)). In the same edit OpenAI removed its limit of 500 lines and wrote: "A large upper bound is not a target". The file itself decreased from 22,047 to 15,311 bytes. One OpenAI source advises the opposite in its words: "Capture edge cases" ([A practical guide to building agents](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)). But there a case is a branch in a numbered step, at the decision point, and the text is about frequent variants. There is no contradiction in substance: the condition is adjacent to the rule that it limits.

The practice of OpenAI agrees with the advice. Of the 44 skills in `openai/skills`, the median size of `SKILL.md` is 7,126 bytes, and the maximum is 37,296 ([openai/skills](https://github.com/openai/skills)). The general base prompt of Codex has 20,903 bytes and contains almost no words in capital letters ([default.md](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/prompts/base_instructions/default.md)). `review-loop`, with 33,493 characters, is larger than each of these base prompts and almost five times larger than the median of the OpenAI skills. Anthropic's own `skill-creator` is approximately 33 KB with 485 lines ([skill-creator SKILL.md](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md)). Thus neither vendor prohibits 33 KB. Text that changes no decisions is prohibited.

## Measurements: the length of one skill does no harm, the number of rules and unnecessary text do

This section contains only measured results. No study measured compliance with process rules (the commit format, the review steps, when to ask a person) as a function of the skill length. All the conclusions below are transferred from other tasks, and this is the primary limit of the evidence.

**All the rules together are obeyed much less frequently than each rule alone.** In ManyIFEval the accuracy for one rule changes almost not at all from 1 to 10 instructions (Claude 3.5 Sonnet: 0.95 → 0.93), but the share of answers that obey all ten falls from 0.95 to 0.48 ([arXiv 2509.21051](https://arxiv.org/html/2509.21051)). In a 2026 paper on rules that can be checked, Sonnet 5 gave a perfect answer in 93.8 % of cases with 10 rules, in 23.8 % with 40 and in 0 % with 80 ([arXiv 2607.19257](https://www.alphaxiv.org/abs/2607.19257.md)). This is one author and one synthetic domain. The arithmetic is this: at 99 % for each rule, one hundred independent rules give approximately 37 % of answers with no miss at all. The authors' fear, "more rules, more misses", is confirmed for rules that apply at the same time.

**Models skip a rule, they do not distort it, and they skip the late ones more frequently.** In IFScale (keywords, 10–500 instructions, 20 models) the best models of 2025 kept 95–98 % at 100 instructions and 43–69 % at 500. The primary error is omission. Late instructions were broken more frequently in the range 100–250 ([arXiv 2507.11538](https://arxiv.org/html/2507.11538v1)). A sentence added to the end of a long text after one more bug is in the weakest position. A repeat of the test on the models of 2026 reports that the limit moved by approximately one order of magnitude, but this is the blog of one supplier, and the task there is simple keywords ([Arize](https://arize.com/blog/llm-instruction-following-benchmark-2026/)). The figure "150–200 instructions" from blogs is not a measured limit.

**There is also evidence to the contrary.** In a study on Claude Code with Opus 4.6, a number of rules from 0 to 50 did not change task success significantly: 60.3 % with no rules, 66.7 % with 50, p = 0.227 ([arXiv 2604.11088](https://arxiv.org/html/2604.11088v2)). There is no contradiction with the previous result: that study measured the success of the task, not compliance with each rule. For the plugin the second is more important, because its skills are a process.

**Unnecessary text on the topic decreases accuracy, a focused input wins.** At Chroma, "Even a single distractor reduces performance relative to the baseline" (not all 18 models were in each experiment), and an input of 300 tokens with the necessary parts was better than the full input of 113 thousand tokens for each model ([Chroma](https://trychroma.com/research/context-rot)). A sentence about a case that did not occur in the given run works as such a fragment. The size of a skill itself, 10–33 thousand characters, is far below all the measured cliffs for context length. The full session makes the risk: tool output, several skills and the shared rules together.

**A detailed and focused skill helps, an all-inclusive skill does not.** SkillsBench is the only test of skills in the `SKILL.md` format that was found. Curated skills increased the success rate from 24.3 % to 40.6 %. By class: "Detailed" +18.8 percentage points, "Compact" +17.1, "Comprehensive" −2.9 (the last class has only 140 observations). One skill gave +17.8 percentage points, two or three gave +18.6, four and more gave +5.9. In software engineering the gain is the smallest, +4.5 percentage points: the model already knows the procedure ([arXiv 2602.12670](https://arxiv.org/html/2602.12670v1)). This is a direct argument against both extreme solutions, and an argument against rules that repeat what the model knows.

**Instruction files change behaviour and cost, but not success.** In the ETH Zurich paper, files of the `AGENTS.md` type (641 words on average) gave no significant increase in success for Claude Code or for Codex, but added 2.5–3.9 steps and approximately 20 % of cost. The agents obeyed the instructions: a tool named in the file was used 1.6 times per task, against less than 0.01 without the file ([arXiv 2602.11988](https://arxiv.org/html/2602.11988v3)). Each sentence is paid for in steps and tokens, whether it is useful or not.

**A skill that did not load does not work, whatever its text.** At Vercel the skill was not invoked in 56 % of cases and gave 53 %, against the same 53 % without it. An index compressed from 40 KB to 8 KB kept 100 % ([Vercel](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)).

**Deletion with a measurement gives few losses.** An author deleted a `CLAUDE.md` of 1,350 lines: of 20 rules that can be checked, two broke, both where the file contradicted the repository. A file of 19 lines plus a skill gave 100 points at 0.696 dollars per run, against 99 points and 1.094 dollars for the full file ([dev.to](https://dev.to/mayankkaul/i-deleted-a-1350-line-claudemd-two-rules-broke-post-404k)). This is one repository, one task and five runs.

**Growth without deletion is a common disease.** In a sample of 2,303 instruction files, the median addition is 57 words per commit, and the median deletion is less than 15 ([arXiv 2511.12884](https://arxiv.org/html/2511.12884v1)). In a sample of 1,867 repositories, the number of instructions increased by 226 %. In a separate, synthetic test bed, when the maintainer kept the reason for each rule, the excess of instructions fell from 211.3 % to 1.4 %. The reasons were kept separately and did not go into the working prompt ([arXiv 2608.11095](https://arxiv.org/html/2608.11095v1)).

**Internal measurements of superpowers** (the data is not published): a list of prohibitions for an error of form "produced clearly more of the unwanted content than the recipe arm", and "trended worse than even the no-guidance control"; "appending a single nuance clause to a winning recipe degraded it from consistent to noisy". With no measurement, the same file says: "Exemption clauses don't scope" ([obra/superpowers](https://github.com/obra/superpowers/blob/main/skills/writing-skills/SKILL.md)). This is the only source that names the mechanism of the "monstrous machine": a rule plus nuance and exemption clauses.

**Evals are noisy too.** In an OpenAI measurement, three repeats of one configuration gave 88, 89 and 86 %, but 23 of 108 cases changed their result between repeats ([Harness-aware evaluation](https://developers.openai.com/cookbook/examples/partners/harness_aware_plugin_evals/harness_aware_plugin_evals)). One run proves neither a failure nor a correction.

## The project's data: the most expensive text is the text that is always read and read in a batch

This is the project's own data, from its repository and from the local count of sessions. It is nearer to the question than any published study, because it measures process rules on these same skills.

**The form of a rule is more important than its presence.** A general line: 0 of 5 Haiku runs; the same rule as a trigger with its concrete results: 5 of 5 (#190). A section that described two levels: 0 of 10; a trigger with one example for each shape: each run that loaded the skill passed, 4 of 4 and 5 of 5 (#192). The explicit word "unasked": 5 of 5, against 0 of 7 on the base text and 0 of 5 on a wider wording. One ordered list with the words "the first step that holds decides" stopped five rounds of contradictions that a list of bullets gave. This agrees with Anthropic's advice about specific signals and with the superpowers recipe "conditional keyed to an observable predicate". Thus the specificity must be kept.

**Cases in prose make new cases.** Prose about the cases of a parser, or a sentence that repeats a rule of a different file, gave a narrower finding in each review round. What stopped it: a cut to the general rule (#97), a rewrite as one principle (#184), and a pointer to the file that already decides (#173). The project's advice since then is to pin the exact cases in tests, not in prose; that advice is not measured. The third review round of a text edit confirmed new defects in the last edit. This is the same mechanism as "a rule plus exemption clauses".

**A measurement before the edit removes half of the work.** One reported gap gave 0 failures of 10 and was closed, a different one gave 9 of 10 and was corrected. The rule against unnecessary growth of the system was not written, because 0 of 5 Opus sessions on the valid case showed such growth (#216). Of 19 open issues, approximately one third were false results of the project's own evals or gaps in the scenario texts. The conclusion: an eval is also code with defects, and "everything into evals" moves the growth from the skill text into the set of checks.

**Loading decides before the text does.** Of 136 review subagents of a TypeScript change (44 of them `/code-review`), 0 started a conventions skill; an architecture lens that reads the conventions files by path read them in 5 of 5 runs (#227). The step with the lens corrected a three-module import cycle that Opus missed in 4 of 5 runs. A prompt that ended with "under 300 words" or "under 900 words" removed no list item in 52 of 52 reports (#409). Not each saving measure works; it must be measured too.

**The cost is not distributed as expected.** In 14 days `github` was loaded in 664 contexts: `SKILL.md` gave 9.7 million characters, and reads of the side files gave 15.2 million. The side files cost more than the `SKILL.md` that sends the agent to them. One take-in reads five files, 82,421 bytes, approximately 27 thousand tokens at three characters per token: `rules.md`, the github `SKILL.md`, `take-in.md`, `tracker.md`, and the review-loop `SKILL.md` for the review (#275). Two of the five are side files of github. Anthropic notes that progressive disclosure pays off for content that is "mutually exclusive or rarely used together" ([Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)). Files that are read together in each run do not meet this condition.

**The shared rules file is probably the most expensive line of the budget.** This is an estimate by the author of the report, not a count by the project: if a file of 11,672 characters went into each of 2,980 transcripts, it gave approximately 35 million characters in 14 days. This is more than `SKILL.md` and the side files of `github` together (24.9 million). Each subagent reads it, including a subagent that does not need most of the rules.

**Context compaction cuts off the tail.** By ADR 0006, after compaction Claude Code returns the first 20,000 characters of each skill; 18 of 18 copies of `architecture` and 26 of 35 copies of `review-loop` were cut. The documentation gives the limit in tokens: the first 5,000 tokens per skill and a shared budget of 25,000 tokens, filled from the most recently invoked skill, and older ones can drop out fully ([Claude Code: Skills](https://code.claude.com/docs/en/skills)). Claude Code counts 4 characters a token here (ADR 0006), so the shared budget is about 100,000 characters. The conclusion of the author of the report: with a 90th percentile of 77,001 characters of `SKILL.md` per context and a maximum of 141,852, the shared budget is used up only in the largest sessions, and there an old skill can disappear fully after compaction. The skills page says nothing about side files. #280 records that Claude Code attaches again the files read last with `Read`, a small one whole, and that a file read with `cat` is not attached again.

**What is missing.** The count measures cost and failed scripts. Nothing measures the misses of rules in real sessions. Half of the authors' question ("more rules, more misses") has no data of its own yet.

## Where Codex and the Fable notes agree and where they differ

An independent Codex run came to the same direction: a smaller core with exact decision criteria, details by condition, deterministic checks, a growing set of regressions. Its formula, "An incident earns an eval case first; it earns runtime prose only when that prose demonstrates value", agrees with the conclusion of the Fable notes about OpenAI. Both runs note separately that the numbers 200 lines, 500 lines, 5,000 tokens and 32 KiB refer to different objects, and that none of them is a measured threshold.

|---|---|---|---|

| Splitting into files | Pays off only for mutually exclusive parts | "Splitting the same mandatory reading into five files does not solve the context problem" | Agreement |

The difference about the reason is resolved as follows. A short reason in one subordinate clause next to the rule stays in the text: Anthropic's example about speech synthesis is one sentence long, and the model generalises from it ([Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)). The history of the incident, the run number and the condition for deleting the rule are kept near the rule, but out of the text that the agent reads. The Claude Code page about skills says "State what to do rather than narrating how or why" ([Claude Code: Skills](https://code.claude.com/docs/en/skills)); this prohibits narration, not a reason in one sentence. The author of the report made this reconciliation; neither vendor states it.

Codex also cites a remark by OpenAI from the GPT-5.4 guide: "Start with the smallest prompt that passes your evals, and add blocks only when they fix a measured failure mode" ([Using GPT-5.4](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-5.4)), and a measurement from the superpowers release notes: a review cycle by a subagent doubled the execution time, and a simpler self-check list gave comparable quality in five versions with five runs each ([superpowers release notes](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)). The second applies to `review-loop` directly.

## Recommendations for the plugin

The author of the report set the numbers in the budgets below, except for 20,000 characters. The sources did not measure such thresholds. The basis is given for each one.

### What goes where

| Place | What goes there | Basis |
|---|---|---|
| The first 20,000 characters of `SKILL.md`, better the first 15,000 | The scope and the trigger; the rules that apply for the full task; the decision rules of the full task in the form "when X — do Y — the result is Z"; one ordered list for each choice; the conditions for reading the side files; one or two examples for a difficult distinction; the reason in one subordinate clause. A rule of one moment goes into the file of that moment (step 7 below) | Measured by the project (5/5 against 0/5 in #190; the ordered list); ADR 0006 (the host keeps 20,000); the advice of both vendors |
| A side file | The procedure of one moment or mode, which is read only in this mode and immediately before the step | The advice of both vendors; the project's data about 15.2 million characters shows the cost of breaking this |
| A script or a validator with a clear error text | All that is checked mechanically and has no exceptions: formats, the order of calls, the collection of state, the parsing of output. The script handles the case, and the error message tells the agent what to do | The advice of Anthropic ("Solve, don't defer") and of OpenAI ("promote the rule into code"); the practice of the project |
| A hook | Only a rule that must always be obeyed at a known moment. Keep the set small. A hook depends on the host; check it separately on Codex | The advice of Claude Code |
| Script tests | The cases of a parser, the input variants, the boundaries | The project's advice, not measured; the measured cure for prose about cases was a cut to the general rule (#97, #184) |
| Evals | Behaviour whose failure is reproduced and repeats; the loading of the skill; the adjacent cases where the edit must not fire. Not wordings and not a regex on words | The advice of OpenAI ("Avoid tests that merely match generated wording"); the project's data about false results |
| An ADR or a record near the rule, out of the text for the agent | The incident, the "before" and "after" runs, the condition for deleting the rule | Measured ([arXiv 2608.11095](https://arxiv.org/html/2608.11095v1)) |
| Delete | A repeat of a rule of a different file; prose about the cases of a script; a retelling of what the model does without a prompt; the history of incidents; exemption clauses, merged into one conditional rule; words of emphasis | The advice of both vendors; the SkillsBench and ETH measurements indirectly |

### The admission rule: when a case gets a sentence

The steps go in order. The first step that holds decides.

1. The failure is not reproduced on the base text (at least 3 failures in 10 runs, the counter checked on a known positive example) — write nothing, close.
2. The eval or the scenario text gives the failure, not the skill — correct the eval.
3. The skill was not loaded or the side file was not read — correct the loading: the trigger, the path, the reading step. Do not touch the text of the rule.
4. The behaviour is checked mechanically and has no exceptions — a script, a validator or a hook. Delete the prose about it.
5. The case is an input variant of a script — a test of the script, with no prose.
6. An existing rule covers the class, but its wording is not clear — rewrite this rule in place: the trigger, the action, the result, the scope or the reason. Do not add a new sentence.
7. The behaviour depends on a condition — one condition on an observable sign, in an ordered list, at the decision point, in the file of the mode where it occurs. Not "a rule plus an exemption clause".
8. Otherwise a new sentence is permitted if it passes a run: a failure before the edit, a success after it, and the adjacent cases did not get worse. Together with it, in the same PR, a sentence to delete is searched for.

The sources give no threshold for step 1. The proposal: a failure in not less than 3 of 10 runs. The basis: in the project the boundary was between 0/10 and 9/10, and at OpenAI one fifth of the cases change their result between repeats, thus 1 of 10 cannot be told from noise. This threshold does not stop a case with data loss or with security.

For a review of the text of a skill or a prompt, the same rule means: a finding that asks for a new case is a hypothesis. Before the edit it needs a failing run. A false fact, as a wrong path or a wrong number, is fixed at once, as *Docs move with the change* in `rules.md` asks. A review of text looks for contradictions and repeats, not for an incomplete list of cases.

The limit of 20,000 characters at three characters per token is equal to approximately 6,700 tokens, that is, above the advice of Anthropic. Thus the target is below the limit.

### How to measure growth and misses

Growth. One script in `make check` counts the characters of each `SKILL.md`, each side file, the shared rules file and each flow by a declared list of files. The values are in a file in the repository. Growth above the recorded value breaks the check until the value is changed in the same PR; thus growth becomes an explicit decision. This is stricter than ADR 0006, which lets a `SKILL.md` under the cap grow up to 20,000 characters, so it needs a new ADR that narrows ADR 0006. The second measure is the net change of characters per PR and the share of PRs with a deletion. The third is the count of loaded characters from the transcripts, which the project already does; repeat it before each release.

Misses. A count is necessary that does not exist now. Select five to ten rules with a mechanical trace in the transcript: the skill is loaded before the first `git commit`; the side file is read before its step; `review-loop` is invoked before the first review; the title of an issue is next to its number. A script counts the compliance rate from the local transcripts for the same 14 days. Before the first report, the counter is checked on a known positive example and a known negative example. A Haiku subagent reads the rules with no mechanical trace on a sample; practitioners advise not less than 100 traces ([hamel.dev](https://hamel.dev/blog/posts/evals-faq/)). The skill load rate is counted first: a sentence in a skill that is not loaded does not work.

Evals. At least 10 runs per variant, as in step 1 of the admission rule, always with a control on the base text. Check on a cheap model and on the primary model, in Claude Code and in Codex: Anthropic warns that a text that is sufficient for Opus can be too small for Haiku, and a text for old models can be excessive for new ones. Keep the set of evals small: "Keep this list small and focused on must-pass checks" ([OpenAI](https://developers.openai.com/blog/eval-skills)).

### How to shorten the existing texts

The cost sets the order: the shared rules file, the side files of `github`, `review-loop`, `architecture`. For each text, each sentence gets one label: decision rule; mechanical; script case; repeat; history; known to the model; exemption clause. Mechanical text goes into a script, cases go into tests, history goes into an ADR, a repeat is deleted, exemption clauses are merged into a conditional rule. The sentences with the label "known to the model" are deleted as a group, and then the existing scenario evals run on Haiku and on the primary model. If the result did not change, the deletion stays. One category changes in one step, otherwise the cause of a shift cannot be found ([GPT-5.2 prompting guide](https://github.com/openai/openai-cookbook/blob/main/examples/gpt-5/gpt-5-2_prompting_guide.ipynb)). The skill text is not edited during a batch of runs.

For the github skill there is a separate question: which of its side files (`take-in.md`, `tracker.md`, `filing.md`, `scout.md`, `merge.md`) each branch needs. There is no reason to split files that are always read together: they are merged and made shorter. Files that are necessary in one branch get an explicit reading condition in `SKILL.md`. `rules.md` and the review-loop `SKILL.md`, which a take-in also reads, belong to other modules and stay apart.

For `review-loop`, splitting by moments is appropriate, but the rules for the full cycle must stay in the first 20,000 characters, and better in the first 15,000: a compaction keeps the start of a skill, and a side file comes back only when it was read last with `Read` and is small (#280).

### First steps

1. Add a size counter with no growth permitted to `make check`: `SKILL.md`, the side files, the flows, the shared rules file.
2. Shorten the shared rules file and give read-only subagents a short variant. Before and after, run the skill load eval separately from other runs.
3. Bring `review-loop` below 20,000 characters: the rules for the full task to the start, the procedures of the moments into side files, deletion by labels with a run.
4. Map the side files of github by branch, remove the repeats between them, and set a target for the flow after the map.
5. Record the admission rule and the budgets in an ADR, not in the text of the skills. In `review-loop`, add one rule: a finding that asks for a new case in the text of a skill needs a failing run before the edit; a false fact is fixed at once.
6. Make a miss counter for five rules with a mechanical trace and get the first number for the same 14 days.

## Conclusion

The primary finding is not in the advice of the vendors. It is in the comparison of that advice with the project's data. The vendors warn about a long `SKILL.md`; in the plugin the primary cost is in the text that is always read and read in a batch, and the side files of github cost more than its `SKILL.md`. The vendors advise "check everything with evals"; in the plugin one third of the open issues are defects of the checks themselves. Thus each saving measure and each check must itself pass a measurement, as already occurred with the word limits of #409.

Three unknowns remain. No one measured compliance with process rules as a function of the number of conditional rules, most of which do not fire in a run; the project's miss counter will give the first such data. The behaviour of a long skill in Codex is not measured, and GPT-6, by OpenAI's words, stops work at a contradiction in a skill, thus an audit of contradictions is more important for Codex than shortening. The models of 2026 hold more instructions and follow each one more exactly; both changes make the deletion of an out-of-date sentence more beneficial than the addition of a new one.
